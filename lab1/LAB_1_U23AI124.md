# Experiment 1: Knowledge Representation — Semantic Network with Inheritance

## 1. Procedure and Result
The semantic network logic, along with its extensions, was implemented in Python using an Object-Oriented approach. Classes `SemanticNode`, `SemanticNetwork`, `Frame`, and `FrameSystem` were used to encapsulate data and logic.

### Code Snippet (`semantic_network_oop.py`)
```python
class SemanticNode:
    def __init__(self, name, parent=None):
        self.name = name
        self.parents = [parent] if parent else []
        self.properties = {}
        self.exceptions = set()

    def add_parent(self, parent):
        self.parents.append(parent)

    def set_property(self, relation, value):
        self.properties[relation] = value

    def add_exception(self, relation, value):
        self.exceptions.add((relation, value))

class SemanticNetwork:
    # ... setup methods ...
    def query(self, node_name, relation):
        node = self.get_or_create(node_name)
        current = node
        while current:
            # Check exceptions first
            for exc_rel, exc_val in current.exceptions:
                if exc_rel == relation:
                    return f"cannot {exc_val}"
            
            # Check local properties
            if relation in current.properties:
                return current.properties[relation]
            
            if current.parents:
                current = current.parents[0]
            else:
                break
        return 'unknown'
```

## 2. Observations
* **How the query for 'penguin can' returns 'cannot fly' even though birds can fly:**
  In the OOP design, the `query` method checks the node's `exceptions` set before its `properties` dictionary. When traversing from `penguin` upwards, the local exception `('can', 'fly')` is detected immediately on the `penguin` node itself, halting the traversal and returning `cannot fly` before the `bird` superclass is ever checked.

* **Why exceptions must be checked before inherited values at every level of the chain:**
  Checking exceptions first is essential to model special cases correctly. If an entity is explicitly defined as lacking a property normally associated with its class, that restriction must have higher precedence. In logic, explicit negative assertions about a specific instance must defeat affirmative default rules inherited from general categories.

* **What the result tells you about default reasoning being non-monotonic:**
  Default reasoning assumes that standard properties hold unless told otherwise. Adding new facts, such as "a penguin is a bird" but "it cannot fly", invalidates the previous conclusion that this specific bird can fly. This is the hallmark of non-monotonic logic: the set of conclusions can shrink when the set of premises grows.

## 3. Justification for Multiple Inheritance Order
In the `FrameSystem`, multiple inheritance was resolved using Breadth-First Search (BFS) starting from the base frame.
**Justification:** When an entity has multiple parent categories (e.g., penguin is a bird and a swimmer), BFS searches all immediate parents before moving to grandparents. This prevents a situation where a distant ancestor on the first path overrides a direct parent on the second path. BFS respects taxonomic distance, reinforcing that more specific traits take priority.
